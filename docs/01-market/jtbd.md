## 이 문서로 내릴 결정

1. **Phase 1 빌드 우선순위 결정 기준이 될 Big Job 1-2개**를 확정한다. 이 Job을 못 푸는 기능은 Phase 1에 들어가지 않는다.
2. 페르소나(정수영 COO / 김민서 CEO / 사용자 / IT 블로커)별 **Functional Job 목록과 P0-P3 우선순위**를 박는다. P0는 Phase 1, P1은 Phase 2, P2는 Phase 3+, P3는 5년간 안 푼다.

4. **명시적으로 안 푸는 Job**(비-ICP의 Job, Phase 4까지 보류할 Job)을 박아 영업·디자인의 스코프 흔들림을 차단한다.

## JTBD 분류 체계 — Big Job vs Little Jobs

이 문서는 두 레이어를 분리한다.

| 레이어                     | 정의                                                                   | 개수    | 우선순위 매김   |
| -------------------------- | ---------------------------------------------------------------------- | ------- | --------------- |
| **Big Job**                | 사람이 Conflow를 "고용"하는 근본 이유. 도구가 바뀌어도 안 변한다       | 1-2개   | 전부 P0         |
| **Functional Little Jobs** | Big Job을 달성하기 위한 구체적 기능 작업 (티켓 만들기, 문서 발급 요청) | 12-18개 | P0/P1/P2/P3     |
| **Emotional Little Jobs**  | 사람이 느끼고 싶은 감정 (안심, 통제감, 압도되지 않음)                  | 5-7개   | UX 입력         |
| **Social Little Jobs**     | 다른 사람 눈에 비치고 싶은 모습 (좋은 운영 리더, 믿을 수 있는 회사)    | 4-5개   | GTM 메시지 입력 |

원칙: **Big Job은 카피로 쓰지 않는다.** Big Job은 우리가 푸는 문제의 정의이고, 카피는 그것을 푸는 방식의 약속이다.

## Big Job — 정수영 COO가 Conflow를 고용하는 이유

icp.md 정수영 페르소나의 "회사 운영 가시성 확보 (CEO 보고용)"와 "1년에 해결하고 싶은 것" 세 가지에서 출발해, 두 개의 Big Job으로 압축한다.

### Big Job #1 — 회사 운영의 단일 화면 (Operating Picture)

> **When** 월요일 9시에 출근해서 이번주 의사결정을 준비해야 할 때,
> **I want to** 한 화면에서 지난주 스프린트 진행 / 막힌 블로커 / 이번주 1:1 일정 / 신규 입사자 상태 / 노무사 검토 대기 문서를 보고,
> **so I can** CEO에게 "지금 회사 가장 큰 블로커가 뭐냐"에 30분 안에 답하고, 이번주 우선순위 3개를 결정한다.

**왜 이게 Big Job인가**

- icp.md COO 페르소나의 일상 고통 4개 중 3개가 이것 하나로 해결됨
- product-vision.md North Star 시나리오 ("월요일 9시... 하나의 화면에서")와 정확히 정렬
- positioning.md 차별화 축 1(도메인 통합도) + 축 2(도메인 횡단 AI)가 같이 풀어야만 답이 나오는 Job — 우리 외에 풀 수 있는 도구가 없음

**4 Forces of Progress** — 이 Big Job에서 사람이 실제로 switch를 일으키는 힘의 균형

| Force       | 내용                                                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Push**    | 1) Slack에서 본 결정이 Jira 티켓에 안 옮겨져 다음주에 같은 논의 반복<br>2) CEO 질문에 답하려고 본인이 3-4개 도구 탭을 매번 열어봄<br>3) 투자사 월간 보고서를 손으로 6시간 들여 만듦<br>4) 신입 입사 시 4개 계정 만들기, 권한 설정에 본인이 반나절       |
| **Pull**    | 1) "월요일 9시 한 화면" 데모를 30분에 보여주면 즉시 이해됨 — 카테고리 교육 비용 없음<br>2) AI가 "지난 스프린트 블로커 + 그 멤버 1:1 피드백"을 한 번에 답함 (단일 도구로 처음 가능)<br>3) 신입 1명 늘어도 Conflow 시트 1개만 추가 — 4개 계정 세팅 사라짐 |
| **Anxiety** | 1) "4개 도구를 하나로 옮기면 한 군데 장애 나면 회사가 멈춘다"<br>2) "Jira 5년치 이슈 데이터는 마이그레이션 시 잃을까"<br>3) "직원들이 Linear/Slack에 익숙한데 갈아탈까"                                                                                 |
| **Habit**   | 1) Slack 채널 200개의 검색 히스토리·핀 메시지·스레드 — 이걸 버리고 갈 결심이 안 됨<br>2) Jira 워크플로우와 자동화 룰을 1년 들여 세팅한 매몰비용<br>3) 노무사가 이미 Flex/엑셀 작업 방식에 익숙                                                          |

**Switch 조건**: Push + Pull이 Anxiety + Habit을 누를 때만 switch가 일어난다. 우리의 임포터(Jira/Linear Phase 1, Slack/Notion Phase 2)는 Habit을 줄이는 무기이고, "월요일 9시 한 화면" 데모는 Pull을 키우는 무기다. Anxiety는 보안 백서 + SLA + 데이터 export 정책으로 줄인다.

**도메인 매핑**: PM + Comms + HR + 문서 4도메인 모두. 한 도메인이라도 Phase 1에 들어가지 않으면 이 Big Job은 불완전하게 풀린다 — 그래서 Phase 1은 **PM + Comms 기본**까지만 약속하고, HR/문서가 빠진 Phase 1의 "한 화면"은 "운영 가시성 알파"로 명명한다.

### Big Job #2 — 회사가 커져도 도구를 안 갈아엎기 (Continuity through Growth)

> **When** 회사가 30명에서 80명, 80명에서 200명으로 1년에 두 단계씩 자랄 때,
> **I want to** 같은 워크스페이스, 같은 권한 모델, 같은 청구 계정을 유지하면서 새 기능만 켜고,
> **so I can** 시리즈 B 펀딩 후 90일 안에 도구 스택 마이그레이션 프로젝트(3개월, 직원 시간 200시간)을 안 돌린다.

**왜 이게 Big Job인가**

- positioning.md 차별화 축 4(마이그레이션 비용 0)의 사용자 측 표현
- icp.md "자생 경로" 가설(ICP-1 → ICP-2 자생 확장률 30%+) 검증의 직접 입력
- product-vision.md North Star "50명에서 500명까지 동일한 도구로 자란다"

**4 Forces of Progress**

| Force       | 내용                                                                                                                                                                                                                                   |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Push**    | 1) 80명 넘어가는 시점에 Notion→Jira, 카카오워크→Slack Enterprise, 엑셀→Flex 동시 마이그레이션 압력<br>2) 매번 권한·청구·통합을 재구성<br>3) 마이그레이션 중 신규 입사자 4명이 와도 이전 도구로 세팅했다가 한 달 뒤 새 도구로 다시 세팅 |
| **Pull**    | 1) 시트 추가만으로 200명까지 자람 — 인사담당자는 Conflow 시트에서만 입사 절차 진행<br>2) HR 도메인은 80명 시점에 "스위치 켜기"로 활성화 (Phase 3)<br>3) 미드마켓 SSO/SCIM도 Phase 3에서 "스위치 켜기"                                  |
| **Anxiety** | 1) "200명 시점에 우리가 우리 회사 깊이를 못 따라오면 어떡하나" (Conflow가 SMB에서 멈출까)<br>2) "미드마켓 보안 인증 (SOC2 Type II, K-ISMS)이 제때 나올까"                                                                              |
| **Habit**   | 1) 도구 갈아엎는 게 회사 성장의 의례(통과의례)라는 통념 — "원래 그런 거다"<br>2) 투자사/이사회가 "글로벌 표준 도구" (Jira/Workday) 쓰라고 권유                                                                                         |

**도메인 매핑**: 권한 모델(공통 인프라) + HR 도메인 활성화 시점 + 미드마켓 보안. 데이터 모델 결정이 모든 차별화의 뿌리이기 때문에 04-architecture/data-model.md가 이 Big Job의 운명을 결정한다.

## Functional Jobs — 페르소나별, P0-P3 우선순위

각 Job은 Job Statement 형식, 우선순위, 도메인 매핑을 모두 가진다. 우선순위 없는 Job은 없다.

| IT-2 | When 보안 검토 보고서를 위에 올려야 할 때, I want to 벤더 보안 백서 / 데이터 처리 위치 / 암호화 정책을 한 PDF로 받고, so I can 검토를 1주일 → 1일 | P0  | (영업 자료: 보안 백서 Phase 1)               |
| IT-3 | When 직원이 퇴사할 때, I want to 모든 도메인(PM/Comms/HR/문서)의 접근권을 한 클릭에 회수하고, so I can 4개 도구 각각 끄는 누락을 안 만든다        | P0  | (인프라: 단일 권한 모델)                     |

| IT-5 | When 한국 공공·금융 고객 진입 시점에, I want to K-ISMS / 망분리 옵션을 받고, so I can 조달 통과한다                                               | P3  | **안 푼다** (Phase 4까지 보류, 그 후 비-ICP) |

## Switch Trigger 시나리오 — 실제 전환이 일어나는 6개 순간

JTBD의 핵심 통찰: 사람은 도구를 고를 때 switch 하지 않는다. **고통이 임계점을 넘는 순간**에 switch 한다. 우리는 그 순간을 알고 30초 메시지를 준비해야 한다.

### Trigger 1 — Atlassian 가격 인상 통보 받은 날

- **상황**: Jira + Confluence + Jira Service 갱신 견적서가 도착. 전년 대비 20-40% 인상.
- **결정적 좌절**: COO가 라이선스 4-5개 누적 청구서를 보고 "직원당 월 10만원을 도구에 쓰고 있다"는 깨달음.
- **30초 메시지**: "Atlassian 라이선스 4개 + Slack + Flex = 직원당 월 25만원. Conflow는 12만원에 PM + Comms + HR + 문서 + AI 횡단까지. Jira 이슈는 마이그레이션 임포터로 그대로 가져갑니다."
- **들어갈 경로**: COO-6 (단일 청구) + Big Job #1 (한 화면) + Trigger의 정량 비교

### Trigger 2 — Slack Connect 외부 협업자 권한이 헷갈리기 시작한 시점

- **상황**: 외주 디자이너 2명, 노무사 1명, 외부 컨설턴트 3명이 회사 Slack에 게스트로 들어옴. 어떤 채널을 누가 볼 수 있는지 COO가 추적 못 함.
- **결정적 좌절**: 내부 인사 논의 채널에 외부 게스트가 한 달째 남아있는 걸 우연히 발견.
- **30초 메시지**: "Slack Connect 게스트는 채널 단위 권한입니다. Conflow는 워크스페이스/도메인/리소스 3단 권한이고, 외부 협업자가 자기 작업만 보입니다. 노무사는 노무사 자료만, 디자이너는 디자인 채널만."
- **들어갈 경로**: IT-3 (단일 권한 회수) + COO-4 (노무사 외부 협업) + EMO-6 (노무사 안 헤매기)

### Trigger 3 — 첫 노무 이슈(권고사직 / 직장 내 괴롭힘 신고)가 카톡으로 새는 순간

- **상황**: 민감 노무 이슈가 카톡 단톡방 / 개인 메일 / 엑셀로 오가다 증거 부족 / 유출 위험 발생.
- **결정적 좌절**: 노무사가 "기록이 흩어져 있어서 대응 어렵습니다"라고 답함.
- **30초 메시지**: "민감 인사 자료는 별도 도메인 + 외부 협업자 권한이 필요합니다. Conflow는 HR 도메인이 분리돼 있고, 노무사가 워크스페이스에 외부 협업자로 들어와 정확한 자료만 보고 작업합니다. 카톡/이메일 왕복이 사라집니다."
- **들어갈 경로**: COO-4 + 차별화 축 3 (KR-first 컴플라이언스)

### Trigger 4 — 신입 4명 동시 입사로 계정 세팅에 본인이 반나절을 쓴 날

- **상황**: 시리즈 B 펀딩 후 한 분기에 신입 8-12명. 매번 Slack / Jira / Notion / Flex / 1Password / Github / Figma 계정 만들기.
- **결정적 좌절**: COO가 반나절을 계정 세팅에 쓰고 "내 일은 이게 아닌데"라는 자각.
- **30초 메시지**: "신입 입사일을 Conflow에 넣으면 4개 도메인 권한 / 채널 / 입사 자료 묶음 / 첫 1:1 일정이 자동으로 생깁니다. 본인 시간 0분, 신입의 첫날 만족도 다른 회사 대비 압도적."
- **들어갈 경로**: COO-3 + EMO-3 + SOC-2

### Trigger 5 — CEO가 ChatGPT에서 회사 데이터를 묻기 시작한 날

- **상황**: 김민서 CEO가 ChatGPT에 "우리 회사 지난 분기 가장 큰 문제 요약해줘"를 입력하다가, "데이터가 여기 없네"를 깨달음. CEO가 COO에게 "AI로 회사 답변 받을 수 있게 해 달라" 요구.
- **결정적 좌절**: 도구 4개의 AI 어시스턴트가 각각 자기 도메인만 봄 — CEO 질문에 답할 도구가 없음.
- **30초 메시지**: "Notion AI는 페이지만, Jira AI는 이슈만, Slack AI는 채널만 봅니다. Conflow는 4도메인을 같이 봐서 '지난 스프린트 블로커 멤버 + 그 멤버 1:1 피드백 + 인사평가 정합성'을 한 번에 답할 수 있는 유일한 협업 툴입니다."
- **들어갈 경로**: COO-2 + CEO-1 + 차별화 축 2 (도메인 횡단 AI)

### Trigger 6 — 80명 직전, 시리즈 B 펀딩 직후 도구 스택 마이그레이션 프로젝트 견적 받은 날

- **상황**: 컨설팅사가 "Notion → Jira, 카카오워크 → Slack Enterprise, 엑셀 → Flex 마이그레이션 3개월, 직원 시간 200시간, 외부 비용 3,000만원" 견적 제출.
- **결정적 좌절**: COO가 "1년 뒤 200명 되면 또 한다는 거냐"는 자각.
- **30초 메시지**: "지금 4개 도구로 가는 대신 Conflow로 옮기면, 80명 → 200명 → 500명 전환에 마이그레이션이 한 번도 없습니다. HR도 200명 시점에 스위치만 켜면 됩니다. 시리즈 C 펀딩 후 도구 프로젝트 안 돌립니다."
- **들어갈 경로**: Big Job #2 (Continuity through Growth) + 차별화 축 4

## JTBD 검증 계획

icp.md "검증 1: 정성 인터뷰 (Phase 0)"를 JTBD 인터뷰 가이드로 구체화. 우리는 의견이 아니라 **마지막 switch 사건의 시점·맥락·감정**을 캔다.

### 인터뷰 대상

- 30-80명 한국 IT 회사 COO / Head of Ops / People Ops 리더 **5명**
- 최근 12개월 내 도구 1개 이상 도입 / 갈아엎기 결정 경험 필수
- icp.md ICP-1 자격 기준 6개 중 4개 이상 충족

### 인터뷰 질문 (JTBD 스타일 — 시점 기반)

1. **"마지막으로 회사에 새 협업 도구를 도입했을 때, 그 결정을 내린 날 회사에 무슨 일이 있었습니까?"** (Switch Trigger 발굴 — 의견이 아니라 사건을 묻는다)
2. **"그 도구를 검토하기 시작한 첫 30분과 결정한 마지막 30분 사이에, 어떤 정보가 결정을 좌우했습니까?"** (Push와 Pull의 균형 측정)
3. **"도구를 도입한 직후 1주일에, '이거 잘못 골랐나' 싶었던 순간이 있었습니까? 어떤 순간이었습니까?"** (Anxiety 사후 검증)
4. **"지난 월요일 9시 출근해서 회사 상태를 파악하기 위해 어떤 도구를 어떤 순서로 열어보셨습니까? 각 도구에서 얼마나 시간을 썼고, 무엇을 못 찾았습니까?"** (Big Job #1 직접 검증)
5. **"신입 1명이 다음주에 입사한다고 가정하면, 본인이 직접 해야 할 일을 시간 단위로 적어주실 수 있습니까?"** (COO-3 / EMO-3 검증)
6. **"노무사 / 외부 컨설턴트와 일할 때, 가장 최근에 정보가 새거나 늦었던 사건은 무엇이었습니까?"** (COO-4 / Trigger 3 검증)
7. **"회사가 1년 뒤 80명, 2년 뒤 200명이 된다고 가정하면, 지금 도구 스택 중 어떤 것을 가장 먼저 갈아엎을 거라고 예상하십니까? 왜 그것입니까?"** (Big Job #2 검증)

### 통과 기준

- 5명 중 **4명이 질문 1에서 Switch Trigger 1-6 중 하나를 자발적으로 언급**
- 5명 중 **4명이 질문 4에서 도구 3개 이상을 열어본다고 답하고, 한 화면 통합에 "30분 안에 검토하겠다"는 의향 표명**
- 5명 중 **3명이 질문 7에서 마이그레이션 비용을 자발적으로 통증 포인트로 언급**
