# Conflow 기술 아키텍처 진단

> 우선순위 4순위 — 엔지니어 관점 (최후방, 사용자 본인이 엔지니어임을 고려해 간결하게)
> 분석일: 2026-06-10

---

## 한 줄 진단

> **현재 스택은 "검증 후 확장"에 필요한 것을 미리 다 들고 들어왔다.** MVP 단계엔 9할 이상이 자산이 아닌 부채다. 단순화 + 정말 필요한 인프라(카톡 연동/모바일/카카오 로그인) 보충이 시급.

---

## 1. TanStack Start (SSR)

**기획 의도:** "대시보드의 초기 로딩 속도 최적화 및 SEO/Type-safety 확보"

**진단:**
- 협업툴 대시보드는 **로그인 뒤 비공개** → SEO 효과 무용
- 초기 페인트(LCP) 이점도 React Query + Streaming Suspense + 적절한 코드 스플리팅으로 거의 대체 가능
- SSR은 운영 복잡도 증가: 엣지/노드 런타임 선택, 하이드레이션 미스매치 디버깅, 쿠키/세션 동기화, Vercel/Fly/자체 서버 결정 부담
- Type-safety는 SSR이 주는 게 아니라 **TanStack Router의 file-based typed routes**가 주는 것 — 이건 그대로 누리되 SSR은 끄거나 정적 빌드로

**권고:**
- **MVP에선 SPA로 단순화** (TanStack Router는 유지, Start의 SSR 모드는 보류)
- 학과 B2B2C 랜딩/문서 페이지만 SSR/SSG 필요해질 때 다시 검토
- 만약 SSR 유지한다면 **하이드레이션 비용을 매주 측정**할 것 — 안 측정하면 자산이 부채로 전환되는 시점을 놓침

---

## 2. Turborepo + pnpm Workspace + FSD (apps/packages)

**기획 의도:** "패키지 간 의존성 관리 효율화 및 빌드 속도 향상, Layered Monorepo"

**진단:**
- 1인 개발자 + 검증 0명 단계에서 모노레포는 **인지 비용 + CI 복잡도가 가치보다 큼**
- FSD의 Core/Business/UI 분리는 좋은 사상이나, **추출 기준이 "재사용 발생"이 아니라 "예측"**이면 dead abstraction이 됨
- A2UI-Ready를 위한 Headless Logic 분리는 매력적이지만, **AI 에이전트 호출자가 실재하기 전엔** 아키텍처 결정 근거가 약함

**권고:**
- `apps/web` 하나 + `packages/shared` 정도로 시작
- **분리 트리거를 명문화:**
  - 동일 코드가 **3번 복사**됐을 때
  - **두 번째 surface**(모바일 앱, 데스크톱, 봇)가 생길 때
  - **외부 노출 API**가 필요할 때
- 그 전까진 단일 패키지 안에서 폴더 컨벤션으로만 FSD 유지

---

## 3. Python 샌드박스 + LangGraph

**기획 의도:** "AI 에이전트가 비즈니스 로직을 안전하게 실행"

**진단:**
- PM·리스크 분석 모두 LangGraph 자동 태스크 할당을 **Phase 2 → Phase 3 강등** 권고
- 샌드박스(컨테이너 격리, 시스템콜 차단, 네트워크 감사, Landlock 등)는 **운영 부담이 사용자 가치 입증 전엔 자산이 아님**
- "회의록 → 액션아이템 드래프트" 같은 **읽기 위주 AI 기능은 샌드박스 없이 LLM API 직접 호출로 충분**
- Python 비중 59.9%가 검증 0명 단계에선 **부채 비율 60%**라는 뜻

**권고:**
- **Phase 1: 통째로 제거.** AI 기능 시연이 필요하면 OpenAI/Anthropic API 직접 호출 + 결과를 사용자가 수동 수락
- **Phase 2: 회의록 요약/액션아이템 추출**만 LLM 단일 호출로 — 그래프, 샌드박스 모두 불필요
- **Phase 3+: 사용자가 자율 에이전트를 "원한다는 증거"가 모인 뒤** LangGraph + 샌드박스 부활

## 5. 빠져 있는 인프라 (진짜 위험)

다음 3개가 LangGraph보다 우선순위가 훨씬 높음:

### 5-1. 카카오 소셜 로그인
- 이메일/비밀번호는 대학생 타깃에서 전환율 사망
- 카카오 디벨로퍼스 + REST API → 1~2일 작업
- **온보딩 실험 자체가 이거 없으면 의미 없음**

### 5-2. 카톡 알림 / 봇
- 옵션 1: **알림톡** (카카오 비즈니스 채널 + 사업자등록 필요, 템플릿 사전 승인, 건당 과금) — 가장 도달률 높음
- 옵션 2: **카카오톡 채널 메시지** (구독자 한정)
- 옵션 3: **카톡 i봇** 데스크 알림 — 대학생 모바일 환경에 부적합
- 옵션 4: **딥링크 + 카톡 공유 OG 카드** — 우회로, 사업자등록 전에 가능
- **권고:** MVP는 옵션 4(딥링크/공유)로 시작, 활성 팀 50개 넘으면 알림톡 사업자 등록

### 5-3. 모바일 반응형 / PWA
- 대학생은 모바일 우선 → 데스크톱 전용은 첫 방문에서 이탈
- TanStack 기반이면 **반응형 CSS + 뷰포트 메타 + PWA manifest** 추가만으로 충분
- 네이티브 앱은 검증 후

## 6. "A2UI-Ready" 슬로건에 대해

- AI 에이전트가 호출하기 쉬운 **순수 함수 분리**는 좋은 습관이고 비용도 거의 0
- 하지만 이걸 **아키텍처 결정의 근거로 삼지 말 것**. YAGNI.
- 진짜 A2UI가 필요해지는 시점: 외부 에이전트(예: Claude/ChatGPT 플러그인, MCP 서버)가 Conflow를 호출하는 시나리오가 실재할 때 — 그때 MCP 서버 한 겹 얹으면 됨

## 7. 우선순위 재배열 (기술 관점)

- 추가 패키지 분리, 신규 추상화

### 지금 단순화해야 할 것

- 모노레포 → `apps/web` + `packages/shared` 2개로 축약

### 지금 추가해야 할 것
1. **카카오 소셜 로그인** (1~2일)
2. **모바일 반응형 + PWA** (2~3일)
3. **카톡 공유 OG 카드 + 딥링크** (1~2일)
4. **이메일/푸시 알림 추상화 레이어** (어댑터 패턴 — 이건 살릴 가치 있음. 나중에 알림톡으로 교체 쉬워짐)

## 1인 개발자 관점 자기 점검

- **"3개월 후 이 코드를 누가 읽으면 이해할 수 있나?"** — FSD 레이어가 비어 있으면 No
- **"내일 공동창업자가 들어오면 어디부터 보여줄 건가?"** — 그게 안 정리되면 모노레포는 빠르다는 환상
- **"이 추상화는 어떤 변경을 대비하는 건가?"** — 답할 수 없으면 제거

## 결론

> **현재 스택은 Series A 회사가 잡을 만한 구조를 검증 0명 단계에서 들고 있음.**
> 기술 부채는 코드뿐 아니라 운영·인지 부담 모두 포함. **단순화는 미덕이 아니라 생존 전략**.
> 가장 큰 레버: ① 카카오 로그인 ② 모바일 반응형 ③ 카톡 공유/알림 — 이 세 가지가 LangGraph/SSR/Turborepo 합친 것보다 사용자 가치가 크다.
