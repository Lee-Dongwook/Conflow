# Conflow Multi-Agent 시스템 개발 가이드

이 문서는 Conflow 프로젝트의 핵심 목표인 Multi-Agent 시스템 구축에 대한 가이드라인을 제공합니다. 특히 초기 개발 단계에서 비용 효율성을 유지하면서 최종적으로 영상 시연을 목표로 하는 전략을 포함합니다.

## 1. Conflow 에이전트의 근본적인 목적 (agent-purpose.md 기반)

Conflow 에이전트는 단순히 협업 UI를 대체하는 것이 아닌, 팀이 놓치기 쉬운 정보를 구조화하여 대시보드, 보드, 수신함에 필요한 데이터를 생성하는 백엔드 워커입니다. 이는 다음과 같은 문제점 해결에 기여합니다:

*   **병목 현상 및 무임승차 방지**: 회의/채팅에서 '막힌 일(Blocker)' 및 담당 공백을 추출하여 알림 및 보드 후보로 제안합니다.
*   **마감 기한 망각 방지**: 논의에서 도출된 마감 기한과 다음 단계를 구조화하여 '이번 주' 또는 인박스에 반영 가능한 형태로 출력합니다.
*   **툴 피로도 감소**: Notion과 같은 복잡한 도구 대신, AI 회의록(한 줄 요약 + 액션 리스트)과 같이 직관적인 형식으로 정보를 제공합니다.

현재 Phase 2 MVP의 에이전트 범위는 '허들(음성) 종료 → 전사 텍스트 → AI 회의록'(`MeetingSummaryPage` 스키마 준수)에 집중하고 있습니다.

## 1.5. 왜 Multi-Agent인가?

Multi-Agent 시스템은 Conflow 프로젝트의 복잡한 협업 문제 해결과 A2UI-Ready 디자인 목표를 달성하기 위한 전략적인 선택이며, 단순히 '오버 엔지니어링'이 아닌 다음과 같은 명확한 이점을 제공합니다.

*   **전문성 및 모듈성**:
    *   각 에이전트는 `meeting_summary`, `blocker_triage`, `retro_insights`와 같이 특정 도메인 또는 작업에 특화될 수 있습니다. 이는 거대한 단일 에이전트보다 개발, 테스트 및 유지보수가 훨씬 용이하며, 시스템의 모듈성을 극대화합니다.
    *   새로운 기능 추가 시, 기존 시스템에 미치는 영향을 최소화하면서 새로운 전문 에이전트를 도입하거나 기존 에이전트를 수정할 수 있습니다.

*   **복잡성 분산 및 확장성**:
    *   실제 팀 협업 환경의 문제는 매우 복합적입니다. 단일 에이전트가 모든 정보를 처리하고 모든 종류의 의사결정을 내리려 한다면, 에이전트 자체가 비대해지고 관리하기 어려워집니다. Multi-Agent는 이러한 복잡성을 여러 에이전트에 분산시켜 관리 가능한 수준으로 낮춥니다.
    *   각 에이전트가 독립적으로 작동하거나 느슨하게 결합될 수 있어, 특정 에이전트의 부하가 높을 경우 해당 에이전트만 확장하여 시스템 전체의 성능 저하를 방지할 수 있습니다.

*   **견고성 및 내결함성**:
    *   일부 에이전트의 오류나 실패가 전체 시스템의 중단을 야기하지 않습니다. 문제가 발생한 에이전트만 격리하여 처리하고, 다른 에이전트들은 계속해서 작업을 수행할 수 있도록 시스템의 견고성을 높입니다.

*   **A2UI-Ready 디자인과의 시너지**:
    *   Conflow의 목표인 A2UI-Ready 디자인은 AI가 시스템과 자연스럽게 상호작용하는 것을 지향합니다. Multi-Agent 아키텍처는 다양한 '스킬'이나 '역량'을 가진 에이전트들이 유기적으로 결합되어 복합적인 사용자 요청에 대응하는 형태로, 이 디자인 철학에 가장 부합합니다.
    *   각 에이전트가 명확한 Input/Output 스키마를 가지므로, AI 오케스트레이션 레이어(Agent Orchestrator)가 각 에이전트를 호출하고 그 결과를 조합하기에 용이합니다.

*   **창발적 지능 및 고도화된 결과**:
    *   각기 다른 관점과 전문성을 가진 에이전트들이 상호작용하고 정보를 교환함으로써, 단일 에이전트로는 달성하기 어려운 보다 고도화된 인사이트나 복합적인 의사결정을 '창발적(Emergent)'으로 도출할 수 있습니다. 예를 들어, '회의록 요약' 에이전트의 결과를 '블로커 트리아지' 에이전트가 활용하여 더 정확한 문제점을 식별하는 시나리오가 가능합니다.

## 2. Multi-Agent 시스템 로드맵

우리의 장기적인 목표는 단일 에이전트를 넘어, 상호작용하는 여러 에이전트가 복합적인 문제를 해결하는 Multi-Agent 시스템을 구축하는 것입니다. 이는 Conflow의 **A2UI-Ready Design** 철학의 정점이라 할 수 있습니다.

| Graph ID          | 상태           | 입력                                     | 출력 (A2UI / API)                 | 비고                                             |
| :---------------- | :------------- | :--------------------------------------- | :-------------------------------- | :----------------------------------------------- |
| `meeting_summary` | **로컬 구현 (v0)** | `meeting_title`, `transcript`, `team_context?` | `overview`, `bullets`, `decisions`, `actions[]`, `next_steps[]` | 현재 구현 중인 핵심 에이전트 기능             |
| `blocker_triage`  | 예정           | 스프린트 컨텍스트, 보드 카드, 인박스     | Blocker 후보 + 근거               | Multi-Agent 시스템의 첫 단계로 다른 에이전트와 연동 고려 |
| `retro_insights`  | 예정           | 회고 카드 텍스트                         | KPT 클러스터·투표 요약            |                                                  |
| `(추가)`           | 예정           | 다른 에이전트의 출력, 외부 정보          | 복합적인 의사결정                 | Multi-Agent의 조율 및 상호작용 로직 구현 필요    |

## 3. 비용 효율적인 개발 전략: Mocking 우선

초기 개발 단계에서는 실제 LLM API 호출 등으로 인한 불필요한 비용 발생을 철저히 지양합니다. 이를 위해, 비용 지불이 필요한 외부 서비스 연동 부분은 **모킹(Mocking)**을 적극적으로 활용합니다.

*   **`CONFLOW_AGENT_MODE=mock`**: `meeting_summary` 파이프라인의 `summarize` 단계에서 API 키 없이 로컬 테스트 및 개발이 가능하도록 합니다.
*   **확장된 Mocking**: 향후 다른 에이전트 개발 시에도, 유료 API 호출이 필요한 부분은 우선적으로 Mocking 로직으로 대체하여 핵심 로직 개발 및 테스트에 집중합니다. 실제 API 연동은 기능이 안정화된 후 필요에 따라 점진적으로 도입합니다.

## 5. FastAPI와의 통합

현재 LangGraph CLI (`langgraph dev`)가 에이전트 서버를 별도의 포트(2024)로 띄우고 있지만, 향후에는 FastAPI(`main.py`)에서 `langgraph_sdk`를 통해 `meeting_summary`와 같은 에이전트 기능을 호출하고 그 결과를 REST API를 통해 반환하며 DB에 저장할 예정입니다. Multi-Agent 시스템 역시 이와 같은 방식으로 FastAPI 백엔드에 통합될 것입니다.

```
START (FastAPI Request) -> Agent Orchestrator (Multi-Agent Logic) -> Individual Agent Runs (e.g., meeting_summary) -> Processed Data -> FastAPI Response & DB Storage
```
